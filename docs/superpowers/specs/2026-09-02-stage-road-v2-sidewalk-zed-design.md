# stage_road v2 — sidewalk class, ZED-referenced road on CAM_FRONT/CAM_BACK, ZED point labels

Date: 2026-09-02. Status: design approved in chat, spec pending review. Record as C35 in
docs/DECISIONS.md when it lands. Supersedes nothing: C33 (stage `road`, publish `cvatroad`)
stays the v1 baseline and its outputs are re-generated by v2.

## 1. What v2 delivers

1. **Road as today.** SAM 3 text prompt `"paved road"` on all 8 cameras, unchanged.
2. **Sidewalk as a class.** A second SAM 3 text prompt, `"sidewalk"`, on all 8 cameras.
   Sidewalk masks are published as their own category in CVAT and as
   nuScenes-lidarseg index 26 (`flat.sidewalk`) on points.
3. **ZED geometry on the two ZED cameras.** CAM_FRONT and CAM_BACK are the ZED cameras. Their
   raw stereo clouds (`samples/ZED_FRONT`, `samples/ZED_BACK`) are read, a ground plane is
   fitted per cloud per keyframe, and height above that plane decides which SAM road pixels
   are really raised (curb/sidewalk) and which points are surface.
4. **3D labels on the ZED clouds.** Each ZED point is labelled road / sidewalk / unlabelled by
   the rule in §5, lifted through its own co-located camera. LIDAR_TOP keeps its road labels
   and gains sidewalk labels by the same rule.
5. **Exports carry all of it.** COCO/CVAT: categories `road surface` (id 1, unchanged) and
   `sidewalk` (id 2). lidarseg: bins for LIDAR_TOP, ZED_FRONT and ZED_BACK sample_data.

### The approved labelling rule (the one design decision made in chat)

A point is **road** only when geometry says it is flat on the fitted plane **and** SAM says
its pixel is road. Flat ground SAM did not call road stays unlabelled; it is never promoted.
Geometry can only remove road claims (raised support carves the 2D mask) and can only confirm,
never invent, 3D road. The stage records per keyframe how much flat ground SAM left out, so
the choice is revisitable with numbers.

## 2. Non-goals

- No SAM 3.1. The cached `facebook/sam3.1` is the multiplex tracker checkpoint Stage 4 drives
  through Meta's `sam3` package (boxes/video); it has no transformers integration and no
  validated text-prompt route here. Both prompts run on transformers' SAM 3 image model.
- No ZED range beyond what the dataroot holds. Every ZED cloud on disk ends at 20.0 m (measured
  on 10 spread keyframes, both channels). The cap was applied when the dataroot was written,
  upstream of this repo. v2 exposes `--zed-range-m` (default 20.0) so a regenerated dataroot
  at 30 m works without a code change. Regenerating the clouds is a separate task.
- No changes to the six non-ZED cameras' 3D story: they keep the v1 LIDAR_TOP plane gate.
- No sidewalk on the six non-ZED cameras' *3D* beyond the LIDAR_TOP rule in §5.3.
- No new CLI switches beyond `--zed-range-m`. Absent ZED channels disable the ZED path
  automatically (§4.3), so no toggle is needed.

| devkit `render_pointcloud_in_image` accepts any `lidar`-modality channel; `get_sample_lidarseg_stats` / `list_lidarseg_categories` hardcode LIDAR_TOP | nuscenes.py | ZED bins load and render per channel; the stock stats call ignores them (documented gap) |
| A sparse category table crashes devkit APIs | C33 review | keep the full 32-row table; only descriptions change |

## 4. Data flow per keyframe

```
for each camera (8):
    road_raw[ch]     = union(SAM3("paved road"))          # v1, unchanged
    sidewalk_raw[ch] = union(SAM3("sidewalk"))            # new
    stats per prompt: fired, n_regions, coverage, score

for each ZED channel present (ZED_FRONT->CAM_FRONT, ZED_BACK->CAM_BACK):
    cloud_ego  = calibrated_sensor(ZED) hop of the RAW cloud, culled to range <= zed_range_m
    proj       = project into the co-located camera (ego pose shared -> 2 hops)
    cand       = points whose pixel is in road_raw[cam]
    plane      = plane_gate(cloud_ego, cand)             # per cloud; refusal -> no ZED labels
    h          = signed height of every projected point above plane
    raised_vu  = pixels of points with RAISE_M < h <= SURFACE_MAX_M
    road[cam]  = carve_raised(road_raw[cam], raised_vu)  # geometry removes, never adds
    sidewalk[cam] = resolve_sidewalk(road[cam], sidewalk_raw[cam])
    zed_road     = flat(h) & in road[cam]
    zed_sidewalk = surface(h) & in sidewalk[cam]

for the six other cameras:
    road[ch] = road_raw[ch]
    sidewalk[ch] = resolve_sidewalk(road[ch], sidewalk_raw[ch])   # road wins, no geometry

LIDAR_TOP (v1 path, extended):
    seen, cand_road, votes_road = paint_cameras(points_ego, road masks)
    _,    cand_sw,   votes_sw   = paint_cameras(points_ego, sidewalk masks)
    gate  = plane_gate(points_ego, cand_road)            # v1 road plane
    road_idx     = gate.kept_index                       # v1 rule, unchanged
    sidewalk_idx = cand_sw \ cand_road, with surface(h) against gate.plane
```

`flat(h)`: `|h| <= RAISE_M`. `surface(h)`: `-RAISE_M <= h <= SURFACE_MAX_M`. Raised for carving:
`RAISE_M < h <= SURFACE_MAX_M`. Points above `SURFACE_MAX_M` inside a road mask (vehicles,
people at mask edges) are counted but never carve.

### 4.1 Two prompts, one model

`Sam3TextSegmenter` loads the model once and gains `__call__(image, prompt=None)`; the
instance default stays `ROAD_PROMPT` so every existing caller and test is unchanged. The driver
calls it twice per image. Cost: forwards double (18,416 more on pilot_1632; v1 took ~32 min for
one prompt, so ~35 min extra). Unit tests inject a fake keyed by prompt.

### 4.2 Mask contest rules (pure functions, already written and tested last session)

- `carve_raised(mask, raised_vu, radius_px=CARVE_RADIUS_PX) -> (mask, n_px)`: erase road
  pixels within `radius_px` of a raised ZED pixel. Identity when no raised points.
- `resolve_sidewalk(road, sidewalk) -> sidewalk & ~road`: road keeps contested pixels.
  Pixels the carve released from road fall through to sidewalk if the prompt claimed them.

Both run on the two ZED cameras; only `resolve_sidewalk` runs on the other six.

### 4.3 ZED join and transform

At `run()` start, load `sample_data.json` and `sensor.json` once. Build
`zed_by_sample[sample_token][channel] = sample_data row` for channels in
`ZED_RING_FOR_CAMERA` (resolved through `calibrated_sensor.sensor_token -> sensor.channel`,
not by filename prefix). For each keyframe, `lidar_sample_data_token -> sample_token -> ZED
rows`. A keyframe with no ZED rows gets `"zed": null` in its road.jsonl row and runs the v1
path plus sidewalk; a substrate with no ZED channel at all records
`manifest["zed"]["channels"] = []` and never enters the ZED branch. Neither is a refusal.

The cloud is read with `read_pcd_bin` (5 x float32; column 4 is luminance, column 5 is 0 in
the raw file) and moved to ego through `Transform.from_nuscenes(calibrated_sensor, LIDAR, EGO)`
exactly as `ingest.py`'s stereo fusion does. Range cull: `norm(xyz_sensor) <= zed_range_m`
before the hop. Projection: `project_lidar_to_image(points_ego, ego_pose, ego_pose, extrinsic,
K, size)` with the *camera's* ego pose on both sides (same sample, same pose).

### 4.4 ZED plane fit and height bands

`plane_gate` is reused for the fit only: candidates are the ZED points whose pixel lies in
`road_raw[cam]`; anchor radius is `min(anchor_radius_m, zed_range_m)`; `min_anchor_points` and
`max_tilt_deg` are the v1 values. On refusal (`no candidates`, thin anchor, steep tilt): the
ZED block records the refusal, no carve happens, the SAM masks stand, the ZED cloud gets no
labels. ZED refusals do **not** degrade the marker: a rear camera blocked by a bus is a normal
frame, unlike a keyframe with no fittable LIDAR road plane. Their count is in the manifest.

Signed height for every projected point: `h = z - (a*x + b*y + c)` from `plane_gate`'s
returned plane. Bands come from §4 with constants in §7.

## 5. Labelling rules

### 5.1 Pixels on CAM_FRONT / CAM_BACK
- road = `road_raw` minus the carve around raised points.
- sidewalk = `sidewalk_raw` minus road.

### 5.2 ZED points
- road (24) if `flat(h)` and pixel in final road mask.
- sidewalk (26) if `surface(h)` and pixel in final sidewalk mask.
- else 0. Points beyond range or outside the image are 0 and counted as unseen.

### 5.3 LIDAR_TOP points
- road (24): v1 rule, unchanged (`plane_gate` kept index over any-camera road candidates).
- sidewalk (26): projects into a sidewalk mask in >= 1 camera, into a road mask in none, and
  `surface(h)` against the LIDAR road plane. No sidewalk labels when the LIDAR plane is refused.

### 5.4 Agreement statistics (per ZED cloud, in road.jsonl and totalled in the manifest)
- `n_flat_in_road`, `n_flat_outside_road` (what SAM missed, the revisit number)
- `n_raised_in_road_raw` (what the carve removed), `n_above_in_road_raw` (tall objects, ignored)
- `n_surface_in_sidewalk`, `n_carved_px`
- `road_agreement = n_flat_in_road / (n_flat_in_road + n_raised_in_road_raw)`

## 6. On-disk outputs (stage tree)

```
stage_road/
  scenes/<scene>/
    masks/<token>.npz            # UNCHANGED layout: one road mask per camera (Stage 5 MaskFile)
    masks_sidewalk/<token>.npz   # same layout, one sidewalk mask per camera
    points/<token>.npz           # v1 arrays + sidewalk_point_index (int32)
    zed/<token>_<CHANNEL>.npz    # one per ZED cloud present
    road.jsonl
  run_manifest.json
  _SUCCESS | _SUCCESS.degraded
```

`zed/<token>_<CHANNEL>.npz` arrays: `road_point_index` (int32), `sidewalk_point_index` (int32),
`seen_point_index` (int32, projected in-image within range), `__n_points_raw__`,
`__sample_data_token__`, `__channel__`, `__frame__ = "ego"`,
`__basis__ = "raw_<channel_lower>_file_order"`. Indices are positional over the RAW file
order, which is what a lidarseg bin needs. Heights are not stored; the plane is in the row, so
they are recomputable from the raw cloud.

`road.jsonl` row additions:
- `cameras[ch]` gains `sidewalk: {fired, n_regions, coverage, score}` and, on ZED cameras,
  `n_carved_px`.
- `sidewalk_mask_path`, `n_sidewalk_points` (LIDAR_TOP).
- `zed`: `null`, or `{CHANNEL: {sample_data_token, n_points_raw, points_path, range_m, plane:
  {plane, tilt_deg, refusal}, n_road_points, n_sidewalk_points, n_seen_points, stats: {...§5.4}}}`.

`run_manifest.json` additions: `spec` bumps to `dhakascenes-pilot/stage_road/v2` (nothing pins
the stage spec string; `require_upstream` checks only the marker spec, and the two exporter
test fixtures that spell v1 are updated);
`prompts: {"road": "paved road", "sidewalk": "sidewalk"}`; `zed: {channels, range_m,
raise_m, surface_max_m, carve_radius_px, plane_fit: "per cloud, plane_gate on road-mask
candidates", n_clouds, n_refused}`; totals gain `n_sidewalk_points_lidar`,
`n_zed_road_points`, `n_zed_sidewalk_points`, `n_images_with_sidewalk`; `known_gaps` replaces
the ZED line with "ZED clouds end at 20.0 m on this dataroot; devkit stats helpers count
LIDAR_TOP only; sidewalk prompt validated on 48 spike images of one scene".

Marker: unchanged protocol (`compose_marker`); ZED refusals are not causes.

## 7. Constants (module level, in the existing v2 block)

| Name | Value | Basis |
|---|---|---|
| `SIDEWALK_PROMPT` | `"sidewalk"` | spike, 44/48 fired |
| `SIDEWALK_INDEX` | 26 | nuScenes-lidarseg `flat.sidewalk` |
| `ROAD_INDEX` | 24 | exporter's existing value, moved to a shared name |
| `ZED_RING_FOR_CAMERA` | `{"CAM_FRONT": 10, "CAM_BACK": 11}` | Stage 1 ring tags; also the channel map ZED_FRONT->CAM_FRONT, ZED_BACK->CAM_BACK |

| `CARVE_RADIUS_PX` | 7 | pixel reach of one raised point |
| `DEFAULT_ZED_RANGE_M` | 20.0 | what the dataroot holds; CLI `--zed-range-m` |

## 8. Exporters and publish

### 8.1 `scripts/export_road_coco.py`
- `categories = [{id 1, "road surface"}, {id 2, "sidewalk"}]`. Id 1 unchanged, so no renumbering.
- For each camera: road annotation from `masks/` as today; sidewalk annotation from
  `masks_sidewalk/` when `cameras[ch].sidewalk.fired` and the mask is non-empty, `category_id 2`,
  `iscrowd 1` + RLE, `attributes.sam3_score` from the sidewalk score.
- `info.description` mentions C35; `cvat_label_attributes` unchanged.

### 8.2 `scripts/export_road_lidarseg.py`
- LIDAR_TOP validation as today, plus `sidewalk_point_index` is required, in range, and
  disjoint from `road_point_index`.
- Every `zed[CHANNEL]` entry is validated the same way: file exists,
  `__basis__ == "raw_<channel_lower>_file_order"`, `__sample_data_token__` and
  `__n_points_raw__` match the row, indices in range, road and sidewalk indices disjoint.
- Duplicate-token check spans LIDAR and ZED tokens together.
- One bin per (keyframe, LIDAR_TOP) and per (keyframe, ZED channel present): uint8 over raw
  order, 24 at road indices, 26 at sidewalk indices, 0 elsewhere. One `lidarseg.json` row per bin.
- `category.json`: full 32 rows; index 24 and 26 descriptions state what this layer assigns;
  the other 30 keep the "assigns it no points" text.
- Refuses a non-empty output table dir as today, so the v1 release root is moved aside first.

### 8.3 CVAT
`cvat_setup.py` unchanged in code. Its C32 preflight only *detects* a label the project lacks
and refuses before creating a task; it does not append, and a label appended by hand arrives
with no attributes (verified 2026-09-02 on CVAT 2.72), so `sam3_score` would be lost on it.
Therefore v2 publishes into a **fresh project**, `DhakaScenes road surface v2`, set through
`CVAT_ROAD_PROJECT` for the `cvatroad` step. `cvat_setup.py` creates it from the export's two
categories with `sam3_score` declared on both labels via `info.cvat_label_attributes`. Project
28 stays untouched as the v1 record. Verify after publish: both labels present, `sam3_score` on
both, road and sidewalk masks render on a CAM_FRONT and a CAM_RIGHT frame.

Deferred alternative, not built now: an `--append-missing-labels` option that appends the
label and clones the sibling label's attribute spec onto it, so one project could carry v1 and
v2 tasks side by side.

### 8.4 `scripts/run_stages.sh`
No new steps. The `road` step passes nothing new (`--zed-range-m` keeps its default). The
marker-summary line gains the ZED totals. Edit the script only when no chain is executing it.

## 9. Error handling

- Missing ZED file named by sample_data: `UpstreamRefusal` before the model loads (dataroot
  integrity), consistent with the stage's "refuse before writing" ordering.
- ZED cloud with wrong record width: refusal naming the file.
- ZED plane refusal: recorded, not fatal, not degrading (§4.4).
- LIDAR plane refusal: v1 behaviour (degrades the marker), now also empties the sidewalk index.
- `--max-keyframes` keeps its non-empty-tree refusal and no-marker behaviour.

## 10. Testing (TDD, fake segmenter, no GPU)

New or extended unit tests in `tests/test_stage_road.py`:
1. Fake segmenter keyed by prompt returns distinct road and sidewalk masks; both files written;
   `masks/` holds only camera keys; `masks_sidewalk/` mirrors the layout.
2. ZED join: synthetic dataroot tables with ZED rows joined by sample_token; keyframe without
   ZED rows -> `zed: null`; substrate without ZED channels -> `zed.channels == []`.
3. Height bands: synthetic ZED cloud on a known plane with a curb strip; assert flat/raised/
   above partitions, the carve region, and the §5.2 labels.
4. Per-cloud plane: two synthetic clouds 0.2 m apart each fit their own plane (the keyframe-800
   fact); a shared fit would misclassify one side.
5. Range cull honours `zed_range_m`; culled points are unseen, never labelled.
6. ZED plane refusal: no carve, SAM masks stand, empty ZED indices, marker not degraded.
7. LIDAR sidewalk rule: raised point in a sidewalk-only pixel -> 26; same point also in a road
   pixel -> not sidewalk; on-plane point in a sidewalk pixel -> 26 (surface band includes flat).
8. npz writers: ZED file fields, basis string, disjoint indices, atomic write.
9. Stats: `n_flat_outside_road` counts flat points SAM missed; agreement ratio.

`tests/test_export_road_coco.py`: two categories, sidewalk annotation carries `category_id 2`
and its own score; road annotation unchanged.

`tests/test_export_road_lidarseg.py`: ZED bins written and indexed; bin bytes 0/24/26 at the
right positions; category rows 24 and 26 described; duplicate token across LIDAR and ZED
refused; disjoint-index violation refused; devkit loads the root and
`render_pointcloud_in_image(..., pointsensor_channel="ZED_FRONT", show_lidarseg=True)` runs
(the existing "empirically confirmed" style, skipped if the devkit is absent).

Existing tests must stay green (34 in the three road suites today; 240 overall).
