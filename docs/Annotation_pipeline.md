# Vision-Only 4D Dataset Annotation Pipeline (Zero-LLM Architecture)

> **Revision 2026-09-12.** The chain this document describes is the one that runs
> today on the Dhaka substrate, not the VESPA blueprint it started from. What
> changed in this revision:
>
> - §1 and §2 now describe the real step chain `0 1 3 3f 3m 4 5 6s 7 8 release`
>   on substrate profile `dhaka6`, with the opt-in arms marked as opt-in.
> - **Stage 6s (approach A)** — one SAM mask → one 3D box from the ZED stereo
>   points that mask owns — replaces VESPA-style BEV clustering on the two ZED
>   frusta. Stage 6 (DBSCAN) is documented as the alternative it now is.
> - `coverage_config: R3` (the two ZED frusta, 25 m cap) is where 3D boxes are
>   claimed at all; the other four cameras stay 2D-only.
> - New §3 states the **known data defects** of this export and the stopgaps
>   applied to them, with numbers.
> - New §4 documents the tooling built for this chain: two read-only viewers, a
>   GT-free evaluation, the batch runner and its dashboard.
> - §6 and §8 replace the old estimates with what was **measured** on this box
>   (RTX PRO 6000 Blackwell). The RTX 4090 estimates are retained, marked as
>   history, because the archived ablations were measured under them.
>
> Every number below carries a source tag; the tags resolve in §10.

This pipeline is a **cost-effective, fully offline, vision-native** adaptation of the hybrid **VESPA** (CVPR 2026) + **AIDE** (CVPR 2024) blueprint. All Large Language Model (LLM) dependencies have been replaced with deterministic heuristics, static dataset priors, and self-supervised visual-embedding methods. Temporal track refinement logic is grounded in **DetZero** (ICCV 2023). 2D mask propagation follows **SAM 2 / SAM 3.1** (ICLR 2025). Open-vocabulary proposals are generated by **Grounding DINO** / **DINO-X Pro** (ECCV 2024); on the Dhaka substrate the proposal role is filled by a closed-vocabulary YOLO11x pair (arm A + arm B), for the reasons in `docs/DECISIONS.md` C23 and C28.

Production runs on an **NVIDIA RTX PRO 6000 Blackwell Workstation Edition** (97,887 MiB) [hw]. The original 24 GB RTX 4090 tier is retained as the prototyping contract and as the hardware every archived ablation was measured on.

## 2. Sequential Technical Steps

### Stage 0 — data probe

Builds the scene allowlist and asserts the export's required channels for the
active substrate profile. `DHAKASCENES_SUBSTRATE=dhaka6` names six ring cameras
plus `LIDAR_TOP`; `ZED_WORLD` sits outside `REQUIRED_CHANNELS`, so its presence
gates nothing here [schemas].

### Stage 1 — ingestion, ground filtering, ZED_WORLD

1. **Single-sweep construction.** `LIDAR_TOP` arrives fused: Livox Mid-360 rings
   0–3 (≈39,936 points/frame) [schemas]. Under `dhaka6` the accumulation window
   is the anchor keyframe alone — this export discards inter-keyframe frames and
   `sweeps/` is an empty directory [paths].

2. **ZED_WORLD ingestion (2026-09-12).** The export's `--zed-world-cloud` channel
   carries both ZED 2i stereo-depth clouds per sample as one channel
   (ring 100 = rear ZED serial 32957407, ring 101 = front ZED serial 35084019;
   intensity = pixel grey), ≈115k points/sample at pixel stride 2, present on
   15,523 of 15,547 samples [paths]. It is written in the **global** frame with an
   identity `ego_pose` and identity `calibrated_sensor`, so the normal nuScenes
   chain must not be applied to it: Stage 1 brings it to ego with the inverse of
   the **same sample's `LIDAR_TOP`** ego pose (verified on sample 500: front ZED
   mean x = +14.8 m, rear −14.5 m after that transform) [paths][spec §3.1].
   A sample with no `ZED_WORLD` row is not an error — the keyframe proceeds
   LiDAR-only.

   Knobs, all Stage 1's and never re-applied downstream [spec §3.1, §3.4]:

   | flag | what it does | default on this run |
   |---|---|---|
   | `--stereo-stride N` | keep every Nth point of each stereo ring, in file order | profile default 8; **approach A runs 1** |
   | `--coverage-config R1\|R2\|R3` | where 3D output is claimed at all | **R3** |
   | `--stereo-z-correction RING:METRES` | constant per-ring z offset, repeatable | **unset** (§3) |
   | `--stereo-pitch-correction RING:DEG:PIVOT_X_M:PIVOT_Z_M` | rigid per-ring pitch about the camera's optical centre, repeatable | **unset** (§3) |

   The stride-8 default existed only to keep Stage 6's DBSCAN alive: one parked
   car in front of a ZED painted ~38k points, and DBSCAN's neighbour graph on
   that single instance reached 53 GB RSS and never finished [schemas]. Approach A
   does not cluster, so it runs at stride 1.

3. **Ground plane.** Angular sector-wise RANSAC per keyframe, inside the
   `dhaka6` z-band (−3.5, −1.0 m), fitted over 3–12 m. Only rings 0–3 and **101**
   vote; the rear ZED (ring 100) puts the road 0.69 m lower at its own camera and
   sinks further with range, so it never votes — its points are still filtered by
   the resulting plane like everything else [schemas]. Points within 0.30 m of the
   plane are discarded, which is why a box bottom can never be placed from points
   (§2 Stage 6s step 8).

4. **`coverage_config: R3` — the two ZED frusta.** R3's admitted azimuth set is the
   union of a front and a rear wedge of half-width `h` = 67.748°/2 = 33.874°
   (the ZED's rectified horizontal FOV), expressed as R2 minus two side blind
   wedges so the existing azimuth machinery needs no new code path; `r_max_m` =
   `STEREO_RANGE_CAP_DEFAULT_M` = 25.0 m [eval_region]. R3 is a statement about
   where 3D boxes are **claimed**, not about which images exist — all six ring
   cameras are still detected, masked and shipped in the 2D layer.

   Measured on `chunk_0010`: **59 s** for 668 keyframes, 135,116,446 → 81,280,937
   single-sweep points (60.2 % retained), ego-compensation residual 4.5e-13 m,
   DEGRADED on 692 rejected sector fits [log-s1].

### Stage 3 / 3f / 3m — proposals and the merge

Arm A is stock YOLO11x over COCO-80, frozen because every archived ablation was
measured with it. Arm B (`3f`, opt-in) is YOLO11x fine-tuned on RSUD20K and emits
exactly `rickshaw` and `cng` — the two most abundant vehicle types on a Dhaka road
and two words COCO does not have. `3m` (opt-in) merges them by **vocabulary
authority, never by score**: arm A is confident on its wrong answers, so a score
contest picks the wrong label on the most abundant indigenous class.

**C35 (2026-09-12, supersedes C34):** arm B's `a rickshaw` now beats arm A's
`a bicycle` on overlap unconditionally. C34 protected a confident arm A bicycle;
measured on chunk_0010, 377 of 1,709 surviving bicycles were protected despite an
overlapping arm B rickshaw, and a quarter of "bicycle" 3D boxes measured 1.2 m
wide — a rickshaw's width. `--protect-arm-a "a bicycle:0.40"` restores C34
verbatim. The visible effect downstream on the same scene: fitted bicycle boxes
269 → 186, rickshaw 1,178 → 1,265 [c35][ev-both].

Measured on chunk_0010: Stage 3 **106 s**, Stage 3f **89 s**, Stage 3m **2 s** [log-0010].

### Stage 4 — box-prompted masks + cross-camera IoA-NMS

One SAM 3.1 mask per merged proposal, in order; ego-frame angular IoA-NMS
suppresses cross-camera duplicates rather than deleting them (the suppressed box
keeps `suppressed_by` and `suppression_ioa`). Masks are written bit-packed per
channel, `(N, 720, 160)` uint8 [spec §4.1]. This is the chain's dominant cost:
**1,502 s** on chunk_0010's 668 keyframes [log-0010].

### Stage 5 — 2D → 3D lift

Paints the Stage 1 single sweep through each Stage 4 mask and writes, per
instance, the rows of the cloud it owns (`points/<kf>.npz` with an `instance_id`
per painted point and a `point_index` into the sweep) plus `lift.jsonl`. This is
the "one object" decision Stage 6s inherits rather than re-deciding. **99–110 s**
on chunk_0010 [log-0010].

**Stage 5 is DEGRADED on every scene of this export**, cause
`ego_motion_between_capture_times_absent` [ev-both]. The exporter copied the
LiDAR ego pose into every camera record, so the ego motion between a camera's
capture time and the LiDAR's is absent from the lift. Stage 5's own manifest
measures both halves on chunk_0010: the largest camera-to-LiDAR time offset is
**36.191 ms** while the largest ego translation delta over the same interval is
**exactly 0.0 m** — that exact zero is the defect, not a stationary vehicle. An
exact-zero delta is a recorded degraded cause rather than a refusal [4f537c6],
because refusing would block every scene of every Dhaka export on a defect no
stage downstream can repair.

### Stage 6s — per-mask stereo boxing on the ZED frusta (approach A)

**One SAM mask → one box. Geometry from the ZED's own stereo depth. No
clustering.** Boxes are produced only for masks on `CAM_FRONT` and `CAM_BACK`,
only inside the range where stereo depth is trustworthy. Every other channel is
written with `status: "out_of_r3"` and `box: null` so the row count matches
Stage 5 exactly [spec §1, §4.1].

**Why it replaces the VESPA path on this substrate.** The Stage 5 → 6 → 7 → 8
chain assumes a dense, single-sensor, accurately calibrated cloud — a 32-beam
Velodyne with ten accumulated sweeps. Here it is fed a single ~40k-point Mid-360
sweep (median 10 LiDAR points per object, 35 % of masked instances with zero)
welded to noisy stereo through tape-measured extrinsics, then clustered as if it
were one clean cloud. All four documented failure modes were confirmed at once on
the day-1 CVAT 3D tasks: boxes stretched along the viewing ray, boxes sunk into or
floating above the road, wrong yaw, neighbours merged or objects missing. Feeding
it better points (the 2026-09-05 fused export) did not fix it — boxes came out
84–93 % elongated along the ray and 55–65 % of true height. **The geometry step,
not the inputs, is what changed** [spec §0].

**Why the ZEDs.** They are the only cameras on this rig with a measured
LiDAR↔camera calibration (`rig.json`: `"calibrated": true`, source
`direct_visual_lidar_calibration`); every other camera is a tape measurement,
`calibrated: false`. They are also the only sensors with dense per-pixel depth
[spec §1].

The geometry, in the order it runs [spec §4.2, cfg]:

1. **Robust depth.** `d_i` = range of each owned stereo point from the ZED's
   optical centre. Keep `|d_i − median| ≤ k·MAD` with `k_mad = 3.0` and a floor
   `mad_floor_m = 0.10` so a flat set is not trimmed to nothing. Fewer than
   `min_stereo_pts = 20` survivors → `status: "too_few_stereo"`, `box: null`.
2. **LiDAR refinement.** If ≥ `lidar_refine_min_pts = 5` of the instance's LiDAR
   points fall inside `[d_near − 2·MAD, d_near + 2·MAD]`, `d_near` is replaced by
   their median and the row records `depth_source: "lidar_refined"`. LiDAR range
   is trusted over stereo wherever it exists on the object. On chunk_0010 this
   fired on **2,792 of 7,701** fitted boxes [ev-both].
3. **Lateral and vertical extent.** Project survivors into the ZED image with K:
   `w_meas = (u_p99 − u_p01)·d_near/fx`, `h_meas = (v_p99 − v_p01)·d_near/fy`.
   **p1/p99, not p5/p95** — the points a mask owns do not reach the object's
   silhouette (ZED depth is invalid or bleeds at depth edges), so point extents
   are biased low by construction, worst for thin objects. Moving the window from
   p5/p95 to p1/p99 raised pedestrian `w_meas/mu` from 0.49 to 0.58 and unclamped
   boxes from 90 to 406 of 4,247 [cfg].
4. **Length from the prior.** `l = prior.l.mu`. Never from the points: stereo sees
   one surface, so the far face is unobservable.
5. **Width and height, clamped ASYMMETRICALLY.** `w_meas < mu − kσ` → `w = mu`
   (`low_to_mu`); `w_meas > mu + kσ` → `w = mu + kσ` (`high`); otherwise the
   measurement stands. `prior_clamp_sigma = 2.0`. Asymmetric because occlusion or
   a stereo hole at a depth edge can only **shrink** the points a mask owns, while
   mask bleed can only grow them and that growth is bounded. Under the old
   symmetric ±2σ clamp, 83 % of chunk_0010's boxes were pinned at the prior floor
   (pedestrians at 0.62 × 1.38 m) [cfg][spec §4.2 step 5].
6. **Yaw.** The footprint's 2×2 covariance supplies the **isotropy test only**
   (`eig_ratio_isotropic = 1.5` → heading along the viewing ray,
   `footprint_isotropic`); otherwise the angle comes from a **closeness rectangle
   fit** (Zhang et al. 2017's L-shape criterion, reused from `stage6_cluster`, not
   reimplemented — PCA answered 52.6° on a 20° fixture because an L-shaped
   footprint's centroid lies off both legs). Two sub-rules:
   - **Single face.** If the fitted rectangle's minor extent falls below
     `single_face_minor_frac = 0.50 × min(mu_w, mu_l)`, only one face is visible
     and the strip *is* a face; which one comes from `|ln(e_major/mu)|` against
     `mu_w` and `mu_l`. Without it, a head-on bus (keyframe 575) had its 2.48 m
     visible rear face taken as the length axis, laying the 11.19 m prior across
     the road. The bar 0.50 was swept on this scene: overall reprojection IoU
     0.2530 → 0.2609, truck 0.0000 → 0.2526 [cfg][50ce150].
   - **Truncation guard.** A width match is only valid when the whole face is in
     frame. If the Stage 4 mask's column extent comes within
     `truncation_margin_px = 4` of either image border, the visible extent is a
     lower bound: yaw falls back to ego forward (0, and yaw is modulo π so the
     same value serves CAM_BACK), `yaw_source: "truncated_ego_forward"`. On the
     pre-fix output of chunk_0010, 925 of 7,701 fitted boxes touched a side
     border and the single-face rule had fired on 455 of them. On the shipped run
     the guard fires **456** times (`n_truncated_yaw`) and the single-face rule
     **384** (`n_single_face_yaw`) [cfg][7f7d639][ev-both].
7. **Centre.** The near face is `d_near` = the **20th percentile**
   (`near_face_percentile`) of the trimmed depths — the median sits 0.3–0.5 m
   behind the nearest point on an oblique view. The centre is that face pushed
   along the ray by the box's **own half-extent in the ray direction**:
   `push = (l/2)·|cos θ| + (w/2)·|sin θ|`, θ = angle between the length axis and
   the BEV ray. Head-on that is `l/2` (the old rule exactly); side-on it is `w/2`.
   The ray passes through the midpoint of the same p1/p99 window that measured
   `w` and `h`, so the centre and the width are one measurement.
8. **Ground snap.** `z_min` = the ground plane's z at the centre's (x, y);
   `z_max = z_min + h`. The bottom is anchored to the LiDAR road, not to the
   points — Stage 1's 0.30 m ground band has already removed the bottom of
   everything.
9. **Range gate.** If the **near face's** BEV range exceeds
   `stereo_range_cap_m = 25.0` → `status: "beyond_stereo_cap"`, `box: null`,
   recorded as `stereo.range_gate_m`. The cap states where this stage's stereo
   evidence is trustworthy, and that evidence is the visible face; gating the
   centre rejected boxes for having a **long prior** rather than bad points, and
   cost 70 of 114 fitted bus boxes once the single-face rule started orienting
   them correctly. With the gate on the near face the same scene fits 200
   [cfg][15b06c8][ev-both].

**Row schema.** Exactly Stage 6's `boxes.jsonl` row, so Stage 7/8/9, the release
and CVAT-3D need no change, plus one additive block (the Stage 3b trick — additive
only, never renamed):

```
stereo = {n_stereo_pts, n_stereo_kept, d_med_m, d_near_m, mad_m, depth_source,
          w_meas_m, h_meas_m, ray_yaw_rad, footprint_eig_ratio, zed_ring,
          n_lidar_in_box, n_stereo_in_box, range_gate_m, frame_truncated,
          truncation_source, single_face{e_major_m, e_minor_m, matched},
          clamp{w, h}}      # each null | "low_to_mu" | "high"
```

**Eight statuses**, of which only `fit`, `too_few_stereo` and `beyond_stereo_cap`
carry a `stereo` block at all; the other five are decided before the geometry runs
and set `stereo: null` [spec §4.3]:

| status | meaning |
|---|---|
| `fit` | a box was produced; steps 1–9 all ran |
| `too_few_stereo` | fewer than `min_stereo_pts` survived step 1 |
| `beyond_stereo_cap` | the near face's BEV range exceeds the cap (step 9) |
| `out_of_r3` | not a ZED channel — never a stereo candidate |
| `channel_disabled` | a ZED channel not in this run's `active_channels` |
| `no_prior` | the class has no measured `{w,l,h}`, so step 4 cannot run |
| `no_points` | Stage 5 painted zero points to this instance |
| `no_ground_plane` | Stage 1 recorded no plane for this keyframe (step 8) |

**`num_lidar_pts` counts painted points, LiDAR *and* stereo, inside the final
box** — `num_lidar_pts_basis` stays `single_sweep_ground_filtered_pre_inflation`
(naming the cloud they are drawn from, so Stage 9's refusal check is satisfied
truthfully) and the manifest additionally carries
`box_fit.num_lidar_pts_basis_detail: "painted_points_inside_box_lidar_plus_stereo"`
plus a matching `known_gaps` line. The split is recorded, not lost:
`stereo.n_lidar_in_box` and `stereo.n_stereo_in_box` are on every `fit` row. The
consequence is stated plainly in §3.

Measured on chunk_0010: **17 s** (rear frustum only) to **54 s** (both frusta)
[log-0010][ev-rear][ev-both].

### Stage 6 — BEV cluster denoising (the alternative)

Still present and still the only producer outside the ZED frusta: project the
painted points onto BEV, run DBSCAN with a per-class ε from the priors file, keep
the largest connected cluster, fit an oriented box by L-shape. VESPA Table 4
records what it is worth on nuScenes — removing cluster denoising drops mAP
46.76 % → 27.86 % [VESPA-T4]. On this substrate it produced the four failure modes
in §2 Stage 6s. `6` and `6s` are **mutually exclusive in one run and the wrapper
refuses both** [run_stages].

### Stage 7 — tracking

DINOv3 re-ID crops plus ICP on matched point sets, Kalman velocity extrapolation
below 15 points. Two changes landed for stereo rows [a8f76de]:

- **ICP registers against a `scipy.spatial.cKDTree`** built once on the target.
  The old code built `src[:, None, :] − target[None, :, :]`; a `stage6_stereo_box`
  instance carries the painted **stereo** returns (`n_points_instance` median 435,
  p90 2,520, p99 23,101, max 28,871), and at 23k × 23k that temporary alone is
  12.7 GB, once per iteration. Same nearest neighbours, no approximation, no new
  dependency. Benchmarked on this box at the sizes above: 23,101 points
  15,312 ms → **10.8 ms** [session].
- **No DBSCAN replay for rows that were never clustered.**
  `reconstruct_cluster_points` promises "the exact points Stage 6's kept cluster
  held"; `stage6_stereo_box` fits one box per mask and keeps no cluster, so
  re-running DBSCAN there does not replay anything — it **invents** a cluster the
  box was never fitted to, at 5.7 s per 23k-point instance. Rows carrying a
  non-null `cluster` keep the replay unchanged; both call sites ask the row.

Before the fix, Stage 7 on chunk_0010 **did not finish in 46 minutes** (111 % of
one core, 19 GB RSS, GPU idle); it was killed by a reboot before it could write a
manifest, so that observation has no artefact behind it [session]. After:
**116.37 s** for 668 keyframes / 7,701 detections — 0.174 s per keyframe,
66 boxes/s, with 4,043 ICP registrations all succeeding and 1,987 Kalman
fallbacks [m7]. On a 1,493-keyframe chunk with 38,893 detections and 14,402 ICP
registrations: **581.97 s** [m7-c29].

Stages 7, 8 and 9 each record **`boxes_source`** in their own manifest, read from
the upstream manifest, so Stage 9 still names `stage6_stereo_box` three stages
downstream; a manifest predating the key answers `"unknown"` rather than naming
the stage that merely passed the boxes on [1b343ee]. The wrapper's Stage 7 block
is handed `--stage6-dir "$(boxes_dir_for_stage6)"` — the same producer choice
Stage 8 and the release already made [725f5cc].

### Stage 8 — static prior box inflation

Sparse boxes are grown toward the class prior means and shifted outward along the
inflation axis so they stay anchored to the observed surface. On chunk_0010:
25,073 rows in, 7,701 boxes, 2,417 triggered, 946 inflated, 1,471 already at or
above the mean, 1,634 clamped axes, mean inflation fraction 0.129, 0 without a
prior — **4.05 s** [m8].

**Priors are authored, not transferred.** `scripts/author_priors_dhaka.py
--from-table` builds `priors_pilot_v0.json` with no template: `{w,l,h}` for the
nuScenes-derived phrases come from the table in §2 below (car 1.93×4.63×1.56,
truck 2.51×6.93×2.84, bus 2.96×11.19×3.44, pedestrian 0.77×0.76×1.72, bicycle
0.60×1.76×1.59, motorcycle 0.77×2.11×1.47, source string
`nuscenes_population_mean_LITERATURE_not_measured`), and the two indigenous
classes take the **operator's** values: `a rickshaw` and `an auto rickshaw`
**l = 2.40 m**, source string
`operator_stated_2026-09-12_not_measured_on_this_data` [1fd5cc7][spec §3.3].
`sigma = SIGMA_FRACTION × mu`, `eps_bev = 0.6 × hypot(w, l)`.
`derived_from.scene_subset` is `"priors"` with a `subset_note` stating no scene was
used — literature values cannot have been tuned on a scored scene.

The file is **bound to its dataroot's metadata fingerprint and refused by any
other**, which is why the batch runner authors one per chunk (§4).

### Stage 9 + release — the gate and the nuScenes export

Gates as printed: `conf >= 0.5, returns >= 5 (single-sweep), BEV <= 2.0x prior
(pre-inflation dims)`. On chunk_0010: 25,073 rows, 17,372 without a box (the
stereo statuses `out_of_r3` 14,509 / `beyond_stereo_cap` 1,755 / `too_few_stereo`
640 / `no_points` 468), 7,701 pre-labels, tiers **auto_accept 4,984 | flagged 477
| rejected 2,240** — and the 2,240 rejected are exactly the boxes with
`num_lidar_pts < 5`, computed independently from the Stage 6 rows. **1.80 s**
[m9].

The release writes 13 nuScenes tables (5,032 `sample_annotation`, 548 `instance`,
668 `sample`, 5,344 `sample_data`) plus `release_meta.json`, `stitch_map.json`,
`double_annotation.json`, `sample_annotation_excluded.json` and
`DELIVERY_NOTE.md`; the devkit check inside the export passes 64/64 and
`check_release` reports 0 errors. With `RELEASE_BLOBS=copy` the blobs are 5,344
real files, 3.76 GB, 0 symlinks and `links=1` — not hardlinks into the dataroot,
and nothing is written into the dataroot. **34.7 s** [rel][session].

## 3. Known data defects and stopgaps

Stated plainly, because every one of them is visible in the output and none is
fixed in this branch.

### 3.1 The front ZED's pose is mis-pitched, and not by a rigid rotation

The export's `CAM_FRONT` (ZED 2i serial 35084019, ring 101) puts its stereo points
below the LiDAR road, increasingly with range. Measured over 120 of chunk_0010's
668 keyframes [ev-cal]:

| window | floor median | slope | implied pitch |
|---|---|---|---|
| 3–15 m | **−1.313 m** | −0.2137 m/m | **−12.06°** |
| 3–40 m | +0.41 m (first bin) → −4.26 m (last) | −0.1200 m/m | **−6.84°** |
| 3–25 m | — | −0.00994 m/m after correction | −9.0974° |

Worst bin 4.046 m past the ground band edge; 69–72 % of ring 101 lies below the
fitted road in the 7–10 m bins. **The angle is window-dependent**, which a single
rigid rotation cannot produce — so the defect is roughly −8° to −12° depending on
where you measure it, not one pitch. A per-block rigidity test (12 blocks of 10
keyframes) failed its own spread bar, and `stereo_pitch_correction` is therefore
`{}`: no point-level correction is applied [cfg][98ceb32].

The rejection is honest about its own weakness, and the config says so: the same
test run on the **LiDAR's own** floor against the LiDAR's own plane gives a wider
spread (0.0741 m/m) than ring 101's (0.0462 m/m), so on 10-keyframe blocks the
estimator is noisier than the 0.020 m/m bar it is judged against. The rejection is
a decision by rule, not a demonstration that the camera is non-rigid [cfg].

The rear ZED (ring 100) is aligned with the LiDAR road: floor −0.322 m over
3–15 m, which **is** Stage 1's 0.30 m ground band edge — its road returns coincide
with the LiDAR road and were deleted by the ground filter [ev-cal].

### 3.2 The front frustum runs without point correction

`active_channels: [CAM_FRONT, CAM_BACK]` (operator directive 2026-09-12). The
front frustum is boxed **without any point-level pitch correction**, because
rotating ring-101 points alone breaks mask → point ownership: the export's
`CAM_FRONT` camera pose carries the same pitch error, so a point-only correction
made **47 % of front instances lose all their points** [cfg]. Front boxes rely on
the **LiDAR ground snap** for z (step 8), and the residual BEV range error is
≈1–2 % (cos 9°). The proper fix is upstream: correct the camera pose and the
points together in a re-export.

### 3.3 Camera-pose corrections exist ONLY in the viewers and the evaluation

`configs/stereo_box.yaml`'s `camera_pose_pitch_correction` is read by
`scripts/view_boxes_3d.py`, `scripts/view_2d.py` and `scripts/eval_stereo_box.py`
and by **nothing under `pipeline/`**. Stage 5 must keep lifting masks through the
export pose so points and masks stay mutually consistent, and Stage 6s boxes are
already correct in the ego frame (ground-snapped to the LiDAR road). What is wrong
is only the pose those consumers **project through** [cfg].

The values were measured in image space, not from the floor: over every fit row
with a scorable hull, `bottom_offset_px` = lowest mask row − lowest projected box
corner row. Both edges are the same physical line (where the object meets the
road), so a channel-wide median is a **pose** residual. On 7,694 fitted boxes of
chunk_0010 [cfg][b09a9dd]:

| channel | n | median offset | implied | correction applied |
|---|---|---|---|---|
| `CAM_BACK` | 4,297 | +20.021 px | +1.1885° | **+1.1885°**, pivot (−0.86481, ·, −0.62055) |
| `CAM_FRONT` | 3,239 | −17.218 px | −1.0349° | **−8.0625°**, pivot (0.81253, ·, −0.73305) |

CAM_BACK had no correction before: the rear ZED's pose is ~1.19° off, which the
floor-based spike could not see, because its road returns had already been deleted
by the ground band. CAM_FRONT's −1.0349° is the residual *after* the −9.0974°
stopgap, i.e. that stopgap **overshoots by ~1°** — hence −9.0974 − (−1.0349) =
−8.0625. The sign differs per camera and was verified numerically on 200 real
boxes each: `d(bottom_offset_px)/d(deg)` is −16.2 px/deg for CAM_BACK but
+16.6 px/deg for CAM_FRONT, because the two cameras look in opposite directions
along ego x.

After correction the residuals are **+0.0668°** (CAM_BACK) and **+0.0141°**
(CAM_FRONT) [ev-both]. Uncorrected, the CAM_FRONT wireframes landed ~150 px above
their objects and its reprojection IoU was 0.0 [cfg][f755bc1].

### 3.4 Camera ego poses are copied from the LiDAR

See §2 Stage 5: the exporter wrote the LiDAR's `ego_pose` into every camera
record, so Stage 5 is DEGRADED on every scene with
`ego_motion_between_capture_times_absent` — camera-to-LiDAR time offsets up to
36.191 ms against an ego translation delta of exactly 0.0 m [ev-both]. Every
mask-to-point association is displaced by the motion that actually occurred in
that window, and every box inherits it. The fix is upstream: **ego-pose
interpolation in the exporter**.

### 3.5 `num_lidar_pts` is not a LiDAR count

Operator decision 2026-09-12: stereo returns count as returns for Stage 9's
"≥ 5 returns" gate. So a box can pass that gate on **stereo points alone**. On
chunk_0010, **5,286 of 7,701** fitted boxes (68.6 %) hold fewer than 5 LiDAR
points; the median box holds 1 LiDAR point and 99 stereo points [ev-both]. The
gate remains truthful about its **basis** and the manifest carries the
`painted_points_inside_box_lidar_plus_stereo` detail, but
`sample_annotation.num_lidar_pts` in the shipped tables carries the mixed count,
and a consumer who reads it as LiDAR will be wrong [tail §5.2].

### 3.6 Upstream fixes this branch does not make

1. **Exporter rig re-calibration** for the front ZED's extrinsic — the rig config
   this export was built from still says `calibrated: false` /
   "INITIAL GUESS -- replace with scripts/calibrate.sh" for that camera [cfg].
2. **Ego-pose interpolation** per camera capture time, which retires §3.4 and the
   degraded Stage 5 with it.

Both are out of scope here; the `stereo_range_cap_m`, `stereo_z_correction_m` and
`stereo_pitch_correction` knobs are stopgaps, and neither knob is a substitute for
either fix [spec §9].

## 4. Tooling

All four are read-only with respect to the pipeline: none writes into a work root,
and none is an annotation tool.

### 4.1 3D viewer — `scripts/view_boxes_3d.py` + `viewer/`

```
view_boxes_3d.py --boxes-dir <stage6_stereo_box> --scene <name> --out <dir> [--serve PORT]
```

Writes one `kf/<index>.json` per keyframe: the cloud decimated to ≤ 80k points as
base64 `[x,y,z,ring]` float32 rows, the `status: fit` boxes with their `stereo`
block, both ZED image paths, K and `T_cam_ego` per camera, the ground plane, and
an `index.json`; then serves `<out>` with `http.server` bound to localhost.
`viewer/index.html` is Three.js from a pinned cdnjs URL, no build step and no npm:
orbit controls, points coloured by ring, boxes as class-coloured wireframes with a
heading arrow, two image panels with the same boxes projected client-side through
K·T_cam_ego (so the projection is checkable against the cloud), a 25 m ring for
the range cap, and a **LiDAR ground disc with 5 m rings, per-ring toggles (front
ZED off by default), a colour-by-height mode and a per-ring height readout**
[32b176f][spec §5].

### 4.2 2D viewer — `scripts/view_2d.py` + `viewer2d/`

Six ring cameras per keyframe in a 2×3 grid, each carrying Stage 3m proposals
(solid outline = arm A, dashed = arm B), SAM mask polygons, and the **3D outcome**
joined from `stage7_track` on `(keyframe_token, channel, proposal_index)`: green
`fit`, grey `out_of_r3` (the expected answer on the four non-ZED cameras, not a
failure), amber `too_few_stereo` / `beyond_stereo_cap` / `no_points`, red for
anything the page has never seen. `fit` rows also get the fitted 3D box projected
faintly back into its own image, through the **same** `project_corners` /
`load_calibs` the 3D viewer uses and the same `configs/stereo_box.yaml` pose
correction, so the two viewers cannot disagree about where a box lands.

Masks ship as polygons, not PNGs (one 1280×720 mask is 1.4 MB unpacked and ~40
vertices as a contour); `--poly-budget` caps a crowded keyframe. Images are
downscaled rather than hard-linked — `/mnt/hdd` and the dataroot are different
filesystems, so `os.link` would fall back to a full copy anyway. Measured on a
1,494-keyframe chunk: **8,964 JPEGs, 657 MB** [v2d]; the export took 87.5 s at
8 threads, which is a session observation — the exporter writes no manifest
[session].

### 4.3 GT-free evaluation — `scripts/eval_stereo_box.py`

```
eval_stereo_box.py --scene <name> [--boxes-dir …] [--config configs/stereo_box.yaml]
                   [--calib-evidence <spike json>] --out-json <f.json> --out-md <f.md>
```

**No ground truth exists on this substrate**, so every number it prints is a
consistency signal, not accuracy. It reports the status histogram and manifest
totals, the clamp rates **and directions**, `depth_source`, the yaw-ambiguity
reasons, support and depth distributions, the per-camera **pitch residual**
(§3.3), and **reprojection IoU** — the box's projected silhouette hull against the
SAM mask that produced it. The markdown is rendered from the JSON of the same
name; no number in the evidence docs is typed by hand. The caveat wording follows
`active_channels`, so a doc cannot claim a frustum was dropped when it was not
[be90577][99fbb94].

Headline on chunk_0010, both frusta, 7,595 scored boxes: overall reprojection IoU
median **0.296** (p10 0.028, p90 0.554); by class, bus 0.496, auto rickshaw 0.490,
rickshaw 0.458, car 0.332, truck 0.257, pedestrian 0.256, motorcycle 0.186,
bicycle 0.126 [ev-both]. The hull is wider than most objects, so a well-placed box
does not score 1; the tail near 0 is where to look.

### 4.4 Batch runner and dashboard

`scripts/run_all_chunks.py` is a queue in front of `scripts/run_stages.sh` and
nothing more — it does not know what a stage does and never writes into a work
root. Four properties matter architecturally:

- **Per-chunk isolated roots.** One generated paths config per chunk gives each
  its own `work_root` / `out_root` / `probe_out_root`. That is also what makes
  parallelism safe: the wrapper takes a `flock` per work root, so two chunks
  sharing one would serialise or overwrite each other's stage trees.
- **Step-level resume from markers.** `run_stages.sh` does not resume on its own —
  it runs every step it is handed, marker or no marker. The runner resumes at two
  levels: a chunk whose release wrote `boxes/release_meta.json` is not dispatched
  at all; a chunk that *is* dispatched gets the requested steps from the first one
  whose marker is missing onward. **A marker after a hole does not count** — a gap
  upstream makes everything downstream of it suspect. `steps_run` and
  `steps_skipped_by_marker` record which was which.
- **Priors authored per chunk.** No step in `run_stages.sh` creates
  `<out_root>/priors/priors_pilot_v0.json`, and the file is bound to its
  dataroot's fingerprint, so one session's file cannot serve the other three. The
  runner calls `author_priors_dhaka.py --from-table --paths <chunk yaml>` for every
  chunk every time; it is idempotent, and a file already bound to the same
  fingerprint is left byte-identical [e9b0ef2].
- **Exports are real files.** `RELEASE_BLOBS=copy` in the chunk overlay, so the
  batch's `<ssd>/exports/chunk_NN/boxes/` holds real bytes on the operator's disk
  rather than links into a dataroot on another filesystem.

`scripts/batch_status.py` serves one local page plus `/status.json` and
`/live.json` over whatever the runner has written. It never writes, never runs
anything and never touches a work root, so it is safe to start, kill and restart
mid-batch.
