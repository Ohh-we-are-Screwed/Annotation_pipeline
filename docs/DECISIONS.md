### C1 — Hardware premise: 4 GB plan vs 24 GB card
```
Status:      RESOLVED (by human, 2026-08-12)
Plan says:   Scope: "3050ti laptop GPU (4 GB VRAM)"; §7.2 total_device_mb: 4096;
             §13.2 lists "It runs on 4 GB VRAM" as supportable.
Disk says:   nvidia-smi: RTX 4090, 24564 MiB, driver 595.84.
Resolution:  The fleet is TWO machines. The 3050ti laptop is real and is where the
             pilot must ultimately run; this 4090 box is where work happens now.
             Option (a): the 4 GB tier stays the binding contract. Every GPU process
             on this machine enforces a synthetic 4096 MiB ceiling
             (DHAKASCENES_VRAM_CAP_MIB -> torch.cuda.set_per_process_memory_fraction);
             every manifest records
             vram_cap: {value_mib: 4096, enforced: "synthetic",
                        physical_device_mib: 24564, device_name: "NVIDIA GeForce RTX 4090"}.
             The "runs on 4 GB VRAM" claim is quotable only after one end-to-end
             confirmation run on the physical 3050ti (declared deferred verification —
             a synthetic cap reproduces neither fragmentation, nor the laptop's
             display-server allocation, nor thermals). Uncapped runs carry
             verified: false. models_production.yaml is now measurable on this card;
             noted, out of pilot scope.
Because:     Without the cap, Phase 5b produces a verified:true VRAM table measuring a
             24 GB machine while models_pilot.yaml says 4096 — the §7.1.1 error class,
             and the pilot would no longer transfer to the device it exists for.
Recorded in: BUILD_PROMPT.md §5-C1; .env.example (DHAKASCENES_VRAM_CAP_MIB);
             requirements-torch.txt header; models_pilot.yaml when written (Phase 2).
Gate:        Phase 5b — measured peaks only count with the cap in force; hard stop
             exercised by deliberately exceeding it. Phase 10 — deferred-verification
             row present in BUILD_STATE.md.
```
